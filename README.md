## 四、正例／反例怎么定义

- **正例**：边界条件应被正确满足，候选可以进入写入／读取；`expected.decision=APPROVE`。
- **反例**：同一类边界的违规形态，候选应被拒绝、要求澄清或延迟；`expected.decision` 为 `REJECT`／`NEEDS_CLARIFICATION`／`DEFER`。
- **普通对照**：不属于七类边界，用来检查规则不要过度拦截；包含普通记忆、重复、纯闲聊、歧义和副作用分离。

注意：正例不是“所有内容都应保存”。例如敏感类正例是“本人明确、范围私人、期限有限的记录”，不是“所有健康内容都自动长期保存”。

## 六、七类边界

| 类别 | 正例在测什么 | 反例在测什么 |
|---|---|---|
| 否定 | 否定、量词、例外、条件被保留 | 否定丢失／反转／范围移动／例外被删 |
| 改口 | 明确更正、随时间改变形成新版本 | 一次选择、一次请假、模糊说法被当成改口 |
| 时间范围 | 当天／一周／过去／人生阶段／周期被限定 | 临时扩成永久、过去写成现在、一次写成习惯 |
| 错人 | 女儿、邻居、老伴、医生的话绑定到正确主体 | 转述他人写成本人；关于本人的转述未请本人确认 |
| 敏感内容 | 本人明确、私人范围、有限期限的记录 | 诊断、用药、风险推断、自动长期化、未经授权分享 |
| 删除后重处理 | 新独立来源／明确重新授权可形成新记忆 | 旧任务重放、旧修订、备份恢复、摘要索引重建复生 |
| 跨用户隔离 | 本人写／读自己的记忆；绑定不影响私人所有权 | 跨租户写／读、伪造 owner、亲属写私人记忆、撤销 grant 后读取 |

## 七、当前能证明什么、不能证明什么

### 能证明

- 用例文件是合法 JSONL，字段、类别、正反例数量与理由码可通过脚本检查。
- 七类边界都有成对的正反例；硬约束类别（错人、删除、跨用户）的反例没有被标成 `APPROVE`。
- 规则与 rubric 对同一批用例给出可核对的判定字段和封闭理由码，具备做盲标的基础。
- 用例覆盖了项目文档中的典型例子：今天不出门、小颗粒改薄片、女儿不吃辣、邻居胃痛、别告诉孩子、删除后旧任务重放、跨用户读取等。

### 不能证明

- **不是人工标注金标**。`expected` 是助手草案；没有第二人独立标注，也没有一致率／κ 报告。
- **不是真实模型评测**。没有跑规则基线、单模型、加审查三方案，没有延迟／token／费用数据。
- **不是真实老人语料**。全部为合成；不能代表真实老人表达、方言、长停顿、改口密度。
- **不是生产安全证明**。没有真实数据库事务、并发 worker、删除传播、备份恢复、真实通知或权限系统。
- **不是统计充分性证明**。155 条只够契约测试与第一轮校准，不足以估计总体错误率。

## 八、怎么运行

### 8.1 校验用例集

```bash
python3 validate.py
```

会检查：

- JSON 可解析、`case_id` 唯一、类别与文件一致；`manifest.json` 的计数与实际一致；
- 七类各 20 条（10 正＋10 反），对照至少 15 条；
- 字段枚举、时间格式、`valid_to >= valid_from`；
- `REVISE` 有目标与 `expected_version`，且与旧记忆版本一致；
- 拒绝／澄清必须是 `NOOP`，且不返回可见记忆；
- 主理由码在封闭词表；`APPROVE` 不能用拒绝类主理由；
- 跨用户／删除／错人的反例不得 `APPROVE`。

### 8.2 生成盲标包

```bash
python3 validate.py \
  --blind-out /tmp/memory-gate-blind.jsonl \
  --sheet-out /tmp/memory-gate-sheet.csv
```

盲标包移除 `expected`、`notes`，只保留 `case_id`、来源、候选、旧记忆、删除状态、请求者与读取请求。标注者只看这份文件＋规则＋rubric。`--sheet-out` 生成 155 行的空白标注表，每名标注者另存一份再填。

### 8.3 双人标注与一致率

1. 每名标注者填一份 CSV，列见 [`annotation-template.csv`](annotation-template.csv)：

```text
case_id,annotator,decision,operation,primary_reason,subject_ok,time_ok,sensitivity_action,note
```

2. 运行：

```bash
python3 validate.py --score annotations.csv
```

3. 输出：每对标注者的百分比一致率与 Cohen's κ（`decision`、`operation`、`primary_reason`、`subject_ok`、`time_ok`、`sensitivity_action`），按七类分别报告，并单列硬约束类别；同时报告标注者与草案标签的差异，便于发现 rubric 歧义。

**v0.1 暂定门槛**（项目内部，不是行业标准）：`decision`／`operation` 一致率 ≥ 0.85、κ ≥ 0.70；`subject_ok`／`time_ok`／`sensitivity_action` 一致率 ≥ 0.90；硬约束子集 `decision` 必须 100% 一致。未达到先修 rubric／用例，不进入模型评分。

> 不要用草案标签回填两份 CSV 来“制造”一致率。那只能测试脚本路径；它既不是真人标注，也不能报告为“两人一致”。

## 九、三方案对照（待运行，不是结果）

M1 要求规则／单模型／加审查三方案的质量—耗时—费用对比。本目录只准备用例和口径，**没有运行结果**。

| 方案 | 做法 | 目的 |
|---|---|---|
| A 规则基线 | 只使用来源、主体、时间、否定关键词、版本、删除、权限等确定性检查 | 知道纯规则能覆盖什么、不能覆盖什么 |
| B 单模型抽取＋相同确定性门禁 | 用同一抽取器产生候选，不加独立语义审查 | 测“抽取＋规则”本身 |
| C 与 B 相同，再加独立语义审查 | 同一来源、候选、存储与规则，多一次审查调用 | 分离“记忆抽取有用”与“多一次审查有增益” |

固定报告：

- 错误候选放行率、正确候选误拒率；
- 主语、否定、时间范围正确性；
- 修订／合并前后信息损失；旧事实错误召回率；
- 删除后复生、跨用户读取、未授权家庭输出；
- 必要澄清触发率、无必要澄清增加老人负担；
- 抽取、审查、提交、召回各阶段延迟、token、每次有效变更费用。

**硬约束用例必须全部通过；语义指标先测基线，再约定容忍范围，不虚构通用 95%／99% 阈值。**

## 十一、已知限制与下一步

### 限制

- 标签是草案；未做真人双标，不能报告一致性达标。
- 用例是合成；没有真实老人语音、方言、情绪、长表达与家庭语境。
- v0.1 是**候选级**用例，不是完整对话级：没有多轮改口、跨会话事件序列、ASR 噪声与说话人切换。下一步应补 20–30 条多轮／多会话序列，并单独报告。
- `MERGE` 只写在规则里，v0.1 没有正向合并用例；合并前后信息损失、关键旧信息保留需要下一版补。
- 没有实现门禁代码；`validate.py` 只检查数据契约，不是门禁运行时。
- 没有跑模型；没有三方案质量／延迟／费用数据。
- 敏感健康的“有限期私人记录”是技术门禁草案，不是医疗或法律结论。
- 删除抑制、重新授权、备份恢复的边界需要在真实存储实验中验证。
- 155 条不是统计充分样本；类别内 10 正／10 反只能做契约与校准，不足以估总体错误率。

### 下一步（按顺序）

1. 乙按 rubric 独立盲标 155 条；甲不参与第一轮。
2. 计算一致率与 κ；对硬约束分歧逐条裁决；修 rubric 歧义。
3. 达到暂定门槛后，把 `expected` 升级为 v0.2 人工金标，并保留原始双标记录。
4. 实现 Pydantic schema 与确定性门禁；把这些用例转成 `pytest` 契约测试。
5. 账号／预算批准后，按第九节跑 A／B／C 三方案；报告分母、版本、错误与费用。
6. 开发集与最终测试集隔离；真实老人语料与合成集分开报告。

## 十二、写作与证据纪律

- 合成数据、草案标签、人工金标、模型结果必须分开写，不能互相冒充。
- 不把“规则写得完整”写成“门禁已实现”；不把“脚本校验通过”写成“模型准确率达标”。
- 不把“某批用例零失败”写成“生产永久零风险”。
- 真实聊天、语音、处方、家庭轨迹与密钥不进入本目录；本目录只有虚构人物与合成句子。
- 修改理由码、判定顺序或一致性门槛时升版本，并说明哪些样本需要重标。
